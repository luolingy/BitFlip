# D2 决策分析：工程库存储方案

> 决策门 D2（见 `docs/DECISIONS.md`），计划要求 **M4 前必须闭环**。
> 本文是决策依据，不是决策本身 —— 结论写在 ADR-0012，可执行方案见 §6。
>
> 编写时点：M2 完成、M3 开始前。此时 `bitflip-project` 只有契约骨架
> （`SCHEMA_VERSION = 1`、`AnnotationKind`、`ProjectMeta::compatibility()`），
> 尚未选存储实现 —— **这正是重开这个决策的最后时机**，
> 一旦 M4 落库，迁移成本就不再是零。

## 1. 这个决策要解决什么

工程库（`.bfp`）要装两类**性质完全不同**的数据：

| 类别 | 内容 | 特征 |
|---|---|---|
| **主数据** | 用户的名字、注释、类型标注、书签、补丁、函数边界、代码/数据标记 | **不可再生**。丢了就是用户几小时的工作没了 |
| **派生物** | 反汇编结果、函数列表、交叉引用、字符串表、CFG | **完全可再生**。重新分析一次就有，代价是 CPU 时间 |

`bitflip-project` 的模块文档已经把这条分界写成了契约，D2 只是在选"用什么装"。

**关键洞察**：这两类数据的**写入模式正好相反** —— 主数据是"小而频繁的随机写"，
派生物是"大而一次性的批量写"。任何单一存储方案都会在一边吃亏。
好的选择不是"哪个方案更好"，而是**怎么把两类数据分开放在各自擅长的存储里**。

### 具体指标（来自 PLAN §M4 验收）

| 指标 | 目标 | 来源 |
|---|---|---|
| 注解落库延迟 | **< 50ms** | PLAN:196 |
| 改名/注释是否触发重新分析 | **不触发** | PLAN:196 |
| 打开已分析目标 | **< 2s** | PLAN:196 |
| 分析中断后重启 | **工程库不损坏** | PLAN:197 |
| 最近打开列表 | 原子写 + 并发安全 | PLAN:198 |

再加两条本项目自己的硬约束：

- **CLAUDE.md §7**：不能假装有结果。存储层不能"写失败但不报错"。
- **磁盘**：C: 仅剩约 2.8GB，带 PDB/DWARF 的目标派生物可能到 GB 级。

## 2. 候选方案

### 方案 A：SQLite（`rusqlite`）

单文件、事务、成熟迁移机制。

- 优点：事务与崩溃恢复是现成的（`WAL` 模式下崩溃不会损坏库）；SQL 让
  "按地址范围查注释""按名字模糊查符号"这类查询变成几行；`rusqlite` 可静态链接，
  不加运行期依赖；生态成熟到"没人会因为选它被质疑"。
- 缺点：**写入是行级 + 页级 B-tree 维护**。注解落库要经过 SQL 解析、事务提交、
  fsync —— 单次写 5–20ms 打底，勉强够 50ms 但没余量。
  派生物（几十万条函数/交叉引用）走 INSERT 会慢一个数量级，且库文件会明显膨胀。
- 缺点：`bundled` 特性要编 C（本机已验证 capstone 的 vendored 编译要 7m38s，
  再来一个会继续拉长冷启动构建）。

### 方案 B：自研 append-only log + 索引快照

主数据追加写日志，内存索引定期快照。

- 优点：**追加写是顺序 IO**，注解落库轻松进个位数毫秒 —— 这是唯一能
  宽裕满足 < 50ms 的方案。派生物可以走**独立文件 + 内存映射**，
  完全不经过事务层。
- 优点：格式完全可控，跨版本迁移可以说清楚（本项目所有跨进程数据都带
  `format_version`，自研格式在这条上更自然）。
- 缺点：**崩溃恢复、并发、迁移、损坏检测全都要自己写对**。
  "自己写对一个数据库"是经典的重复劳动重灾区。
- 缺点：查询能力几乎为零。"找出所有落在函数 F 范围内的注释"
  要自己在快照里维护二级索引。

### 方案 C（推荐）：分层 —— SQLite 管主数据，独立文件管派生物

即 **A + B 的组合，但按数据性质切分，而不是按存储技术偏好切分**。

- **主数据 → SQLite**。它是"小而频繁的随机写 + 需要查询 + 绝不能丢"，
  正好是 SQLite 的主场。50ms 预算够用，而且未来加"按注释搜索"零成本。
- **派生物 → 自研独立文件**（每个目标一个 `<hash>.bda` 派生物文件，
  写时复制 + 原子 rename 发布）。它是"大而一次性的批量写 + 只按地址查"，
  不需要事务，只需要"要么是旧的完整版本，要么是新的完整版本"——
  这正好由**原子 rename** 提供，不需要重做数据库。

## 3. 为什么是 C，而不是"先用 SQLite 把功能做对"（D2 原文的倾向）

原倾向是"先用 SQLite 把功能做对，M6 后按基准决定是否引入自研日志层"。
**这个倾向在 M4 的语境下是错的**，理由有二：

### 3.1 它把最大的风险推到了不可回退的点之后

原倾向的隐含假设是"以后换存储是件局部的事"。但在 M4 之后不是:
派生数据一旦进了 SQLite，派生物的表结构、写入路径、查询路径会全面依赖 SQL。
到 M6/M7 派生物规模上来（PDB/DWARF、字符串表、交叉引用）再换，
要动的是分析管线的下半段 —— 而这期间用户已经建了工程库、存了注释。
**迁移一个已经装着用户主数据的库，比一开始就分开贵得多。**

### 3.2 更要命的是：SQLite 管派生物会破坏 M2 刚建立的诚实性契约

这是本文最重要的一条发现。

M2 建立了一个核心契约：**反汇编结果带可信度分层**
（`reachable` vs `linear_only`），且这些结果**在重新分析后可能改变**
（换个扫描策略、修一个解码 bug、加一种种子来源）。

如果派生物和主数据同库，会发生两件坏事：

1. **派生物写入失败会连累主数据的事务**，反之亦然。而派生物是**可以失败**的
   （磁盘满、分析被取消），主数据**绝不能**失败。同库就是把"可失败的"
   和"不可失败的"绑在一根绳上。
2. 重新分析要"先删旧派生物再写新的"，这在同一个库里是个大事务；
   如果中途崩溃，用户打开工程库会看到**半新半旧的分析结果** ——
   而它看起来和完整的没区别。这正是 CLAUDE.md §7 要禁止的
   "让界面看起来完整"。

分开存则天然解决：派生物写到临时文件，全部成功后原子 rename 覆盖。
崩溃时旧文件完好无损，**要么全新、要么全旧，不存在中间态**。

## 4. 方案对比

| 维度 | A：纯 SQLite | B：纯自研日志 | **C：分层（推荐）** |
|---|---|---|---|
| 注解落库延迟 | 5–20ms（勉强） | < 5ms | < 5ms（主数据仍是 SQLite，但写入路径短） |
| 注解落库延迟（含查询需求） | 好 | **差**（要自己建索引） | 好 |
| 打开已分析目标 < 2s | 好 | 好 | 好（派生物 mmap 直接映射） |
| 崩溃不损坏 | 好（WAL） | **要自己写对** | 好（SQLite 保主数据，rename 保派生物） |
| 分析中止不留半成品 | 差（同库大事务） | 好 | **好（rename 是原子的）** |
| 大派生物的体积效率 | 差（B-tree 膨胀） | **好** | **好（裸紧凑格式）** |
| 磁盘占用 | 中 | **低** | 低 |
| 实现工作量 | 低 | **高** | 中（SQLite 部分低 + 派生物格式简单） |
| 查询能力 | **强** | 弱 | 强（主数据）/ 够用（派生物只按地址） |
| 未来加"注释全文搜索" | 零成本 | 要自己写 | 零成本 |
| 迁移路径 | 有成熟机制 | 自己写 | 各自独立、互不影响 |

## 5. 结论与触发条件

**采纳方案 C。** 具体地：

1. **`.bfp` 主数据文件 = SQLite**（`rusqlite`，`bundled` 静态链接）。
   表结构见 §6.2。**只装主数据**。
2. **派生物 = 独立文件** `<target-hash>.bda`，自研紧凑格式，
   写临时文件 + 原子 rename 发布。**可以整体删除重建，删了不心疼**。
3. **`bitflip-project` 的公开 API 不暴露 `rusqlite` 类型** ——
   这句是硬约束：`bitflip-core` 是对外稳定契约，
   嵌入方不该被迫依赖 SQLite。存储实现放在 `bitflip-project` 内部。

**明确不做的事**：不引入 ORM，不做"存储后端抽象层"。
目前只有一个后端，抽象层是纯粹的投机成本；等真有第二个后端
（比如"只读的导出快照"）再抽，那时形态会清楚得多。

**重新评估的触发条件**（任一满足即重开 D2）：

1. 基准显示注解落库的 P95 **持续 > 50ms**（即 SQLite 确实撑不住）；
2. 派生物格式在 M5/M8 演化出**按范围频繁查询**的需求
   （例如"列出所有落在 [a,b) 的交叉引用"），而 mmap + 二分不够用；
3. 用户提出**多目标联合检索**（"在所有打开的工程里找这个字符串"）——
   那需要真正的数据库，而不是每目标一个文件。

## 6. 可执行方案（M4 落地清单）

### 6.1 文件布局

```text
<workspace>/projects/<target-hash-prefix>/<target-hash>.bfp    # SQLite 主数据
<workspace>/projects/<target-hash-prefix>/<target-hash>.bda    # 派生物（可删）
<workspace>/projects/<target-hash-prefix>/<target-hash>.bda.tmp # 写入中的临时文件
```

用**内容哈希**而不是路径/文件名做标识 —— 这条 `bitflip-project` 已经定死了：
"目标身份按内容哈希，不是 size+mtime"。同一份文件换个名字打开，
注释应当还在；改一个字节，注释应当失效并明确告知。

### 6.2 SQLite 表结构（v1）

```sql
PRAGMA journal_mode = WAL;      -- 崩溃安全 + 并发读
PRAGMA synchronous  = NORMAL;   -- WAL 下的性能/安全平衡点
PRAGMA foreign_keys = ON;

CREATE TABLE meta (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
-- 必需键：schema_version, tool_version, target_sha256, target_size,
--         created_at_unix, analyzed_at_unix

CREATE TABLE annotations (
  id          INTEGER PRIMARY KEY,
  address     INTEGER NOT NULL,      -- u64 地址（SQLite 的 INTEGER 是 64 位）
  kind        TEXT    NOT NULL,      -- AnnotationKind::as_str()
  -- 名字/注释/类型/补丁文本；补丁为 NULL
  text        TEXT,
  -- 补丁的原始字节（十六进制），非补丁为 NULL
  patch_hex   TEXT,
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL,
  UNIQUE(address, kind)              -- 同一地址同一类只有一条
);

-- 范围查询的主力：按地址找注释是最高频的操作
CREATE INDEX idx_annotations_address ON annotations(address);
```

**为什么 `address` 用 `INTEGER` 而不是 TEXT**：内部一律 `u64`
（CLAUDE.md §4），字符串化只发生在 wire 边界。存 TEXT 会让范围查询
退化成字符串比较。

### 6.3 派生物文件格式（`.bda`，`format_version = 1`）

```text
偏移  内容
0     magic "BFLPDA\0\0"
8     format_version  u32
12    flags           u32
16    target_sha256   [32]u8     -- 与 .bfp 交叉校验，不匹配就丢弃重建
48    table_count     u32
52    表目录：table_count × { kind u32, offset u64, length u64 }
...   各表数据（紧凑、可 mmap、按地址排序）
```

- **按地址排序 + 二分查找**满足派生物的全部查询需求（"这个地址属于哪个函数"）。
  不需要 B-tree，不需要 SQL。
- **不写回主数据**。派生物里出现的名字全部是**分析产物**，
  用户改过的名字在 `.bfp` 里是权威 —— 渲染时合并
  （这正是"M2 的 `reachable` 分层"同一思路的延伸）。
- **校验 `target_sha256`**：目标变了就丢弃重建，而不是给出错误的旧结果。

### 6.4 写入流程（关键：原子性）

```text
分析开始
  → 创建 <hash>.bda.tmp
  → 流式写入派生物（可取消：取消就删掉 tmp）
  → 全部写完 + fsync
  → 原子 rename tmp → <hash>.bda      ← 这一刻之前，旧文件一直可用
  → 更新 .bfp 的 analyzed_at_unix
  → 提交事务
```

**崩溃在任何一步都不产生"半成品"**：`.bda` 要么是旧版本、要么是新版本。
`.tmp` 残留由下次打开时清理（它不是有效文件，不会被误读）。

### 6.5 验收测试（M4 必须有的）

1. **延迟**：注解落库 P95 < 50ms（1000 次写入实测，不是估算）。
2. **不触发重新分析**：改名/注释后重新打开，分析次数不增加。
3. **打开 < 2s**：对 M2 的 100MB 级目标，已分析过的打开时间实测。
4. **崩溃不损坏**：在写入各阶段（含 rename 前）强杀进程，
   重开后 `.bfp` 可读、`.bda` 要么旧要么新、无中间态。
5. **目标变更失效**：改目标一个字节，旧注释被明确标记为失效
   （而不是静默套用到新目标上）。
6. **schema 迁移**：`schema_version` 不匹配时给出明确路径，
   不是静默失败或崩溃。

## 7. 与现有代码的接口

这次决策**不需要改 M2 的任何代码**，只需确认边界：

- `bitflip-project` 保持"只依赖 `bitflip-core` 的公开类型"，
  新增 `rusqlite` 依赖不泄漏到 `bitflip-core`。
- `Disasm` 的 `notes` 已经是"降级说明要浮到 UI"的通道，
  派生物过期/不可用应当走同一条路，而不是新的错误通道。
