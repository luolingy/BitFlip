# 决策记录（ADR）

> 只记录**已决**与**待决**的架构决策。已决项如需推翻，追加新条目而不是改写旧条目。

## 已决

### ADR-0001 · 技术栈：Rust 全栈 + 内嵌 Web SPA

**状态**：已决（用户确认）
**决策**：分析核心、服务、CLI 全部 Rust；UI 是 TypeScript + React + Vite 的 SPA，
用 `rust-embed` 编进二进制；`bitflip <target>` 起本地 HTTP 服务并打开系统浏览器。

**理由**
- 跨平台交付只需要"为每个平台构建一个 Rust 二进制"，不需要原生 GUI 外壳（用户明确要求 UI 走本地网页服务）。
- 运行期零依赖：不需要 Node、不需要附带 DLL/SO 集合。
- 反汇编/分析是 CPU 与内存密集型，Rust 是唯一能同时满足性能与安全的选择。

**代价**
- 构建期依赖 npm 构建 SPA（CI 里 `npm ci && npm run build`）。
- 浏览器是唯一 UI 载体：布局/渲染能力受 Web 限制，超大数据渲染需要虚拟滚动与游标分页（已纳入设计）。

**被否方案**
- `Rust napi 插件 + Node/Hono 服务`（adi 路线）：可复用 adi 的 TS 代码，但分发依赖 Node 打包
  （adi 的 `build-bundle.mjs` 需要给 pkg 打补丁、内联 yoga.wasm），脆弱且继承 adi 的内存/性能短板。
- `纯 Rust + 服务端直出 HTML`：依赖最少，但大型反汇编列表与 CFG 图视图实现代价过高。

### ADR-0002 · 仓库形态：独立仓库，`bitflip-core` 可嵌入

**状态**：已决（用户确认）
**决策**：BitFlip 是独立 git 仓库；`crates/bitflip-core` 是对外稳定 API，
可被其他项目通过 git submodule / path / crate 依赖嵌入；服务层与 UI 是它的消费者之一。

**理由**：用户要求"作为子模块"；同时避免"能嵌入"沦为口号 —— 只要 API 稳定、分层单向，嵌入成本自然低。

**约束**
- `bitflip-core` 不依赖 `axum`/`tokio`/`rust-embed`，也不暴露 SPA 类型。
- 公开 API 的破坏性变更需要 CHANGELOG + 版本号提升。
- 参考实现 `temp/adi` 的风格：它的 CLI/核心分层是清晰的，可作为 API 分层惯例的参照。

### ADR-0003 · 格式优先级：除 Apple 可执行文件外全覆盖，Mach-O 推迟到 M10

**状态**：**已由 ADR-0017 取代**（Mach-O 与 Apple 容器改为 M12 立项）——
保留本条目是为了留下决策轨迹，不要按它排期。

**决策（当时）**：M1–M9 支持 PE（exe/dll/sys/obj/lib）、ELF（exec/so/o）、ar 归档、raw 固件、COFF 对象；
Mach-O（含 `.app` bundle、dylib、fat/universal）列入 M10 TODO，不在主线里程碑验收范围内。

**理由**：用户明确"除了苹果的可执行文件，其他都要，苹果的文件写进未来 todo"；
同时本机无 macOS 环境，Mach-O 的验证成本高（只能做解析层验证，无法链接真实产物）。

**约束**：`Container`/`Object` 抽象预留 `Fat` 变体，但 M0–M9 不实现其解析，
避免为未实现的需求扭曲主设计（见 ARCHITECTURE §3）。

### ADR-0017 · Mach-O/`.app`/IPA 与 APK/DEX 立项为 M11、M12（取代 ADR-0003）

**状态**：已决（用户确认）
**日期**：2026-08

**决策**：新增两个主线里程碑，`docs/PLAN.md` §4 有完整的范围、验收标准与非目标：

- **M11 · Android：APK / DEX**（用户要求"完全逆向"）。
- **M12 · Apple：Mach-O / `.app` / IPA**（用户要求"完全逆向"）。
- M10 保持"未来 TODO 池"不变，但其中"Mach-O / `.app` / fat"一条**移入 M12**。
- **IPA 依赖 Mach-O，Mach-O 必须先做完**；M11 与 M12 **互不依赖，可并行**。

**理由**：

1. 用户明确要求把"apk 完全逆向"和"app/ipa 逆向"加入任务表，且 Apple 目标不再只是 TODO。
2. **两者都不该塞进 M10**。M10 是"不承诺、按需排序"的池子；而这两项是**用户明确要求
   的交付**，混进池子会让"没排期"和"不承诺"变成同一个状态，用户无从知道它到底做不做。
3. **两者都不是"再加一种容器"**。M11 引入的是**基于寄存器的字节码**（无栈帧、无机器码、
   无重定位），要动 `bitflip-arch` 与 `bitflip-analyze` 的执行模型假设；M12 引入的是
   **目录作为可打开目标**（本项目第一次），要动 `Session` 的打开路径。
   把这种量级的工作写成 M10 里的一条 TODO，是在用格式的相似性掩盖工作量的不相似性。
4. **IPA 依赖 Mach-O 是硬依赖，不是排期偏好**：`.ipa` 只是 ZIP，里面是 `.app` 目录，
   目录里是可执行文件。没有 Mach-O 解析，IPA 支持就只是一个会列出文件名的解压器。
   所以顺序写进计划，避免有人"先做简单的 IPA 那层"从而产出一个没有分析价值的里程碑。

**约束**：

- `Container`/`Object` 抽象需要扩展两处：ZIP 容器（APK/IPA 共用）与**目录容器**
  （`.app`）。扩展方式必须在动 `Session` 之前单独设计。
- 两个里程碑都**不做重打包/重签名**（与 M9 "写回是破坏性操作"同一条理由）。
- 本机无 macOS 与 Android 运行环境：所有 fixture 必须在 Windows 上交叉生成；
  生成不了的部分**显式 SKIP 并给出生成命令**，不能静默变绿（CLAUDE.md §7）。

### ADR-0019 · M11：优先复用现成库、只自研缺口；APK 容器先做、native 库复用 ELF

**状态**：已决（用户确认"如果 apk 可以使用现有的库减少工作量，也是可以的"）
**日期**：2026-10

> **更正**：本 ADR 的第一版写的是"**DEX 解析器与 Dalvik 解码器都必须自研**"，
> 理由是"没有可用的轮子"。**那个前提是错的**。因为零实现曾基于旧文本起步，
> 这里直接改写而不是再开一个 ADR 叠在上面 —— 留一份已知错误的决策在原地
> 比改它更有害。

**错在哪（值得记下来的方法论）**：旧文本的依据是**点名检查了三个已知 crate**
（`dex` 冻结 / `dalvik` 只是反汇编器 / `smali` 是 GPL-3.0）后就归纳为
"没有可用的"。改用 **crates.io 搜索 API 按关键词枚举**之后，
`droidsaw-dex`（BSD-3-Clause，45k LoC）与 `apk-info`（Apache-2.0）立刻浮出，
且**实测在真实 APK 上可用**。
教训：**"我查过几个候选"不等于"没有候选"** —— 归纳结论必须写明搜索方式，
否则一次三点采样会被当成普查结论沿用下去。

证据：`docs/research/apk-dex-library-survey.md`（含实测数字与复现命令）。

**背景**：ADR-0017 把 APK/DEX 立为 M11，并明确"扩展方式必须在动 `Session`
之前单独设计"。本次调研回答了那个"单独设计"，同时**用真实样本纠正了
三处我原本会写错的范围假设**。

**决策 1：能用现成库的地方用现成库；只自研真正的缺口。**

旧的候选表（`smali` GPL-3.0 / `dex` 冻结 / `dalvik` 不建模型 / `lief` 构建期下载）
里每一条的否决理由**依然成立**，所以那三个不能用仍然是对的 ——
错的是"因此没有可用轮子"这一步推论。真正的可用项：

| crate | 许可 | 覆盖 | 实测结论 |
| --- | --- | --- | --- |
| `droidsaw-dex` | **BSD-3-Clause** | `parser`/`decode`/`cfg`/`xrefs`/`mutf8`/`opcodes` | 类数 7643 **与手读 header 一致**；解码在 **3000/3000** 个真实方法上"恰好铺满 `[0,insns_size)`"；CFG 直接产出我要的边类型 |
| `apk-info`（+`-zip`/`-axml`） | **Apache-2.0** | 容器 / 清单 / 资源 / 签名检测 / ABI | 1867 条目、ABI 名单、multidex **逐项与独立基准一致**；二进制清单还原成 29 392 字节 XML |
| `zip` | MIT | ZIP | 已在选型结论里；解出的 `.so` 是 ELF64 `EM_AARCH64` |

两棵依赖树的许可闸门都实跑过：强著佐权 **0**
（唯一朴素正则命中的 `r-efi` 是 `MIT OR Apache-2.0 OR LGPL-2.1-or-later`
这类**析取式**许可，按 MIT/Apache 使用即无著佐权义务）。

**决策 2：`Arch` 新增 `Dalvik`，新增与 capstone 并列的 DEX 解码后端 ——
但"新增后端"不等于"自己写后端"。**

后端必须独立这一点是**硬约束**：实测 capstone 0.18 的架构只有 18 个
（ARM/ARM64/MIPS/X86/PPC/SPARC/SYSZ/XCORE/M68K/TMS320C64X/M680X/EVM/MOS65XX/
WASM/BPF/RISCV/SH/TRICORE），**没有 Dalvik/ART**。
所幸边界很窄：`Decoder` trait 只有 `spec()` + `decode_one()`
（`decode_many` 有默认实现），而 `droidsaw-dex` 的
`decode::parse_code_item` 已经给出带 `addr`/`Opcode`/`size`/`target`/`pool_idx`
的指令流。**要写的是适配层（转成项目的列式 SoA 表示），不是解码器本身。**

**决策 2b：`droidsaw-dex` 的反编译层不接入。**

它的 `emit`/`emit_dex`/`sugar`/`r8_inversion`（约占一半体积）做**类型推断与
Java 源码生成**。ADR-0018 已判定这类输出按定义就是推断，直接展示违反 §7。
好在这些是**并列的公开模块**，切得开：只用事实抽取层
（`parser`/`decode`/`cfg`/`xrefs`/`mutf8`/`opcodes`），反编译层不引。

**决策 3：里程碑按"价值/成本"排，不按格式复杂度排 —— APK 容器先做。**

理由是**成本差一个数量级**：APK 里 `lib/<abi>/*.so` 就是普通 ELF，
而 ELF 路径**已经能用**。所以"能列出成员 + 解压 `.so` + 复用现有 ELF 路径"
几乎零新解析代码，却立刻拿到 native 库的完整逆向能力；
而 DEX 结构模型 + Dalvik 解码器是这条线上最大的一块。

顺序：**M0（ZIP 容器 + native 库复用 ELF）→ M1（DEX 结构模型）→
M2（Dalvik 解码器 + CFG）→ M3（AXML + arsc）**。

**决策 4：v041 容器 DEX 不做，直到遇到真实样本。**

**实测两个真实 APK（1867 / 1624 条目）的 6 个 dex 全部是 `dex\n035\0`、
`header_size = 112`。** v041 里"所有 `*_off` 相对容器起点而非本 DEX 头"
是整个格式里最容易全错的一处（单文件测试全绿、第二个 DEX 全错）。
既然真实样本用不到，就不做 —— 但**解析器遇到 041 必须明确报"版本尚未支持"**，
不能按 035 的规则错误解析（"说的就是真的"）。

**决策 5：真实样本推翻的三处假设，记在这里防止以后又被"想当然"写回去。**

| 原以为 | 实测 | 影响 |
| --- | --- | --- |
| 现代 APK 用 v041 容器 DEX | 全是 035 | 砍掉整个 v041 分支（决策 4） |
| `extractNativeLibs=false` ⇒ `.so` 未压缩、需对齐 | **压缩方法全是 DEFLATE（37/37、20/20），STORED 为 0** | 必须解压；**不做**"从 APK 直接 mmap `.so`"这条路，也不做 zipalign 对齐校验 |
| ABI 集合是 Soong 那 5 个 | 还有 legacy **`armeabi`** | ABI 名单要含 `armeabi`，未知目录名记 `notes` 而不是丢弃 |

另外确认了 `.so` 是 `EM_AARCH64` 的 ELF64、`AndroidManifest.xml` 是二进制 XML
（type `0x0003`）、`resources.arsc` 头与文档一致（`0x0002`/headerSize 12）。

**需要新增的概念**（现有 `Object` 模型表达不了，详见
`docs/APK-DEX-DESIGN.md` §4）：

1. **合成地址空间**。DEX 没有虚拟地址：数据是文件偏移，代码是 code unit 索引。
   仍用 `u64`（项目约定），但必须写明是**合成地址**，
   且**反解函数要有单测** —— 否则用户看到 `0001000000001234` 会当成真实地址。
2. **要接进来的 CFG 边类型**：`SwitchCase`/`SwitchDefault`（来自 payload）与
   异常边（一个 try 块可有**多个** handler 目标）。
   **更正：这些不必自己造** —— `droidsaw-dex` 的 `EdgeKind` 已经是
   `FallThrough | Branch | SwitchCase(i32) | SwitchDefault | ExceptionHandler(TypeIdx) | ExceptionCatchAll`，
   并带 `ExceptionRegion { start_addr, end_addr, handler_blocks }`。
   要做的是**投影到项目的 CFG 表示**，不是新增语义。
3. **多 dex 的符号键**：`(dex_index, index)` 复合键（multidex 下同名类可能并存）。

**明确不复用**：DEX 无栈帧（寄存器机），所以**不能**跑现有 `frames` 路径
（`scan_frames` 依赖 `UnwindEntry` 与前导 `push/pop` 扫描，对 DEX 全部不适用）；
也没有节权限 / `image_base` 概念，`analyze` 里"按 RVA 落在哪个节"的逻辑要对 DEX 短路。

**约束**：

- **引用现成库的代价必须写在明处**（本次实测结论，细节见调查报告 §4）：
  - `droidsaw-*` **极新**（首发 2026-04，总下载 945/611），且从 0.1.0 的
    0 行到 1.0.0 的 43 333 行只隔 6 周。**本次只验证了有限几条不变量，
    没有逐字段核对全部输出**。因此：新依赖必须配**项目自己的黄金测试**
    （对着真实 APK 断言类数/方法数/覆盖率等不变量），不能只信库的自述。
  - 发布的 crate **不含测试**（`exclude = ["/tests"]`），所以"179 个测试"
    这类说法**无法从制品验证** —— 引用时不得把它当证据。
  - `apk-info*` / `rusty-axml` / `dex-parser-rust` **声明了许可但没随包发
    LICENSE 文件**。Apache-2.0 的分发义务要求附许可原文，
    真要依赖就得从各自仓库取回 LICENSE 并随产品分发。
  - `droidsaw-apk` 为签名验证引入 `rsa`/`p256`/`ecdsa`/`cms`。若只需要
    "检测签名块存在"，优先用 `apk-info-zip::signature`，避免背这套依赖。
- 结论里必须区分"**存在** v2 签名块"与"**已验证** v2 签名"；后者未实现，
  按 §7 报 `NotYetImplemented`。不做重打包/重签名（同 ADR-0017）。
- `.cdex` / `.vdex` / `.oat` 明确拒绝；**不要**写死网上抄来的 magic 字符串
  （原文本次未取得，见参考文档 §10）。
- 13 项 `UNVERIFIED` 在实现时必须落成"要么取原文验证、要么在结论里标未知"。
- **样本量为 2 不等于"现网没有 041"**（两个样本可能同源）。
- **新依赖必须过 `scripts/check-licenses.py`**（两棵树本次已实跑：强著佐权 0）。

**参考**：`docs/research/dex-apk-format-reference.md`（字节级实现参考）、
`docs/APK-DEX-DESIGN.md`（分层与验收）。

### ADR-0020 · DEX 视图自成一类：不把 `Disasm` 泛化成 trait

**状态**：已决（M11 的 M2 **动手前**定；`docs/APK-DEX-DESIGN.md` §M2 要求的那个决定）

**背景**：设计文档把 DEX 指令文本的渲染列为"本方案里唯一一处现成库帮不上的
**结构**问题"，并给了两条路：（A）新增 DEX 渲染路径；（B）把渲染器抽象成 trait
（`bitflip-core` 的 `Disasm.renderer` 现在是 `Option<Arc<CapstoneDecoder>>`）。

**决定**：选（A），而且不是"在渲染处并列一条 DEX 分支"，而是**DEX 的视图自成一类**
（视图类型与它自己的 `render_insn` 都放在 DEX 侧），`Disasm` 保持只有机器码一种形态。

**依据 —— 先看 `Disasm` 由什么构成，再看 trait 能不能表达**：

| `Disasm` 的组成部分 | 对 DEX 是否成立 |
|---|---|
| `AddrSpace`（由段/节映射出的线性地址空间） | **不成立**：DEX 没有段权限、没有 `image_base`；一条方法的字节码在 `code_item` 里，按 16 位码元寻址 |
| `InsnIndex`（全空间稀疏指令索引，按地址） | **不成立**：DEX 的指令天然按"方法"分组，地址是方法内偏移 |
| 扫描种子（入口点 / 导出 / 函数符号） | **不成立**：DEX 没有这些，代码入口在 `class_data` 里 |
| `ScanCoverage` / `ScanStats`（可达 vs 仅线性） | **语义不成立**：Dalvik 不需要"猜哪里是代码" |
| `renderer: Option<Arc<CapstoneDecoder>>` | 不成立，但这**只是最后一格** |

**关键理由**：把 `renderer` 换成 trait 只能让**最后一格**对 DEX 成立，前四格照样不成立。
那正是"让类型看起来能装 DEX、实际产出无意义结论"的做法 —— 与 M1 拒绝把 DEX 塞进
`parse_object`（`ObjectKind::Dex` 的 `arch` 恒为 `None`）是同一条理由。
**泛化一个不成立的抽象比拒绝它更危险**：后者在调用处报错，前者会静默产出。

**代价对比**：

- （B）要改 `bitflip-core` 的公开 API（`Disasm`，而 CLAUDE.md §4 明确它是对外契约，
  改动要记 CHANGELOG 并考虑兼容），换到的只是"能调用"，不是"结论正确"；
- （A）的代价是 CLI/导出层将来要认两种视图。但那个分叉本来就存在 ——
  "反汇编一个 `.so`"与"列出一个 DEX 的方法"是**两件事**，不是一件事的两种参数。
  所以它不是新增复杂度，而是不再假装两者是同一种东西。

**什么时候重新评估**：若出现**第三种**非机器码格式（.NET IL、WASM 字节码…）也要接进来，
那时该抽象的是"**扫描 + 视图**"这一层（`AddrSpace` / `InsnIndex` / 种子三者构成的接口），
而不是渲染器。届时依据来自两个真实需求，而不是一个想象中的。

**本 ADR 不定的事**（不在这里假装定好）：DEX 视图在 CLI/导出里**怎么呈现**
（新子命令，还是 `--member classes.dex` 自动切换视图）留到 M2 实现末尾 ——
依据是"用户在命令行上想表达什么"，现在还没有证据。

**更正（2026-10-15，M2a 实施期间据实记录）**：上面的**背景**照抄了设计文档当时的
说法 —— "DEX 指令文本渲染是本方案里唯一一处现成库帮不上的结构问题"。**那句话与事实
不符**：`droidsaw-dex` 2.0 有 `smali` 模块，`smali::fmt_instruction(&Instruction,
&DexFile) -> String` 与 `DexFile::emit_smali` 都能直接产出（含符号解析的）smali 文本。

结论不变、理由要换：

- **不用它的真实理由**是它在拿不到符号时**静默产出占位符** —— `fmt_type_ref` /
  `fmt_field_ref` 失败时写 `"?"`，字符串引用失败时写 `"<invalid>"`。这正是 CLAUDE.md
  §7 禁止的"用默认值冒充结果"：读的人分不出"文件里就是 `?`"和"我们没解析出来"。
  我们自己的渲染路径在解析不出符号时保留可数的池索引，并把失败次数交回调用方。
- 次要理由：`fmt_instruction` 每条指令返回一个 `String`（§4 的 SoA 取向），且签名里
  带 `&DexFile`，会把库的池类型带进我们的渲染调用面。
- ADR 的**决定**（DEX 视图自成一类、不泛化 `Disasm`）依据的是 `Disasm` 前四格对 DEX
  不成立，与本条更正无关，故不变。

已加守卫：`tests/dex_library_boundary.rs` 用**另一条独立的清单与另一套措辞**拒绝
`droidsaw_dex::smali`（理由是"静默占位符"，不是"推断"），避免以后有人顺手接进来把
`?` 漏进用户输出。教训与 §6.11 同形：**先核实"库做不到"，再据此写理由** ——
否则文档里会留下一条经不起查证的技术判断，而它看起来很像事实。

**参考**：`docs/APK-DEX-DESIGN.md` §M2、ADR-0019。

### ADR-0008 · 开发环境网络：仓库内 crates.io 代理 + 仓库内 CARGO_HOME

**状态**：已决（M0 期间的环境适配）

`AcquireCredentialsHandle` 失败（`SEC_E_NO_CREDENTIALS`），而 Node 的 TLS 正常。
因此提供两件事：

1. `scripts/crates-proxy.mjs`：Node 实现的 crates.io 稀疏索引 + 包体代理（默认 `127.0.0.1:8765`，
   磁盘缓存在 `.crates-proxy-cache/`）；
2. `scripts/cargo.ps1`：把 `CARGO_HOME` 指向仓库内 `.cargo-home/`，
   该目录的 `config.toml` 把 `crates-io` 替换为本地代理。

**理由**

**代价与限制**
- 本机所有 cargo 命令必须经由 `scripts/cargo.ps1`（或自行设置 `CARGO_HOME`），否则会尝试写 `C:\Users\...\.cargo` 而失败。
- `.cargo-home/config.toml` 里的源替换必须**始终生效**：先用 `--offline` 拉到的包不会出现在
  `crates-io` 源下，混用会报 "no matching package named ... found"。
- `Cargo.lock` 入库，保证后续可离线、可复现构建。

### ADR-0010 · SPA 构建提供不依赖子进程的备用路径

**状态**：已决（M1 期间的环境适配）
**决策**：SPA 有两条等价构建路径，产物一致：

1. `cd web && npm run build`（vite）—— 普通开发机与 CI 使用；
2. `node scripts/build-web.mjs`（rolldown 直出 + 单独复制 CSS）—— 受限沙箱使用，
   脚本内自校验产物大小并确认 React 运行时确实被打进去。

**背景**：M1 需要在浏览器里验证段/节结构视图，而在本机沙箱下 `vite build` 必然失败：

```
spawn EPERM
  at optimizeSafeRealPathSync (vite/dist/node/chunks/node.js)
```

vite 在加载配置时会 `execFile` 解析真实路径，而沙箱禁止 Node 创建子进程
（CLAUDE.md §6 trap 6）。这不是项目缺陷 —— 在普通终端里 `npm run build` 正常。

**理由**
- 段/节视图是 M1 的验收项，不能因为"本机构建不出来"就不验证。
- 备用路径只依赖已安装的 `rolldown`（vite 8 的底层打包器），不引入新依赖、不下载任何东西。
- 产物与 vite 版本**同源同依赖**：同一份 `src/`，只是少了文件名哈希。

**代价与限制**
- 产物文件名不含内容哈希，因此不能依赖长缓存；对内嵌进二进制的场景无影响。
- 样式必须由脚本单独复制（rolldown 已不再支持把 CSS 打进 JS bundle），
  故入口拆成 `src/entry.tsx`（无 CSS import）与 `src/main.tsx`（vite 用的带 CSS 入口）。
- `web/index.html` 入库并被脚本读取，保证标题/lang/meta 只有一处定义；
  资源引用固定为 `/assets/app.js` 与 `/assets/app.css`，脚本会校验这一点。
- **两条路径都必须保持可用**：改前端构建相关配置时要同时验证。

### ADR-0013 · D1 已决：脚本层用 rquickjs，WASM 推迟到有真实插件分发需求时

**状态**：已决（M6 末的决策门；完整测量与分析见
[`docs/D1-SCRIPT-ENGINE-ANALYSIS.md`](./D1-SCRIPT-ENGINE-ANALYSIS.md)）

**决策**：M7 的脚本层嵌入 **`rquickjs`（QuickJS，JavaScript）**。
`wasmtime` **不在 M7 引入** —— 推迟到 M8 之后出现真实的第三方插件分发需求时再评估。

**理由（按重要性排序）**

1. **验收 1 是"话很多"的负载，JS/Lua 的主场。** "识别所有调用 `memcpy` 的函数
   并重命名参数注释"要遍历几千个函数、上万条交叉引用，每次都穿过脚本↔宿主边界。
   这在 A/B 里就是普通函数调用；在 wasmtime 里每次都要过 ABI、把地址与字符串
   在**线性内存**里编解码。后者不是"慢一点"，而是**脚本 API 的每个形状都要为
   ABI 让路**。
2. **M7 会反复改脚本 API，而 ABI 的迭代税在这个阶段最贵。** 交付物里的
   "自定义视图数据源"这类需求会不断长出新的宿主函数。A/B 里加一个函数是加
   一个绑定；wasmtime 里是改 ABI + 重新编译所有脚本 + 处理版本兼容。
3. **前端已经是 TypeScript。** 同一门语言意味着 `web/src/api.ts` 已有的 wire
   类型定义可以生成脚本 API 的类型声明，用户写脚本时有补全与类型检查，
   宿主侧也少维护一套心智模型。这是 Lua 与 WASM 拿不到的。
4. **实测代价差一个数量级**（本机冷构建 / 单文件体积）：
   rquickjs **221.9s / 1.14MB**、mlua 280.3s / 0.52MB、
   wasmtime 997.7s / 11.67MB（默认特性 1980.5s / 14.63MB）。
5. **wasmtime 的 MSRV 是 1.96.0，正好等于本机工具链，零余量。** 这会把我们
   绑在"工具链只能升不能降"的状态上，且它一抬 MSRV，之后的构建就会在某次
   `cargo update` 后突然失败。

**明确否掉的原倾向**：D1 原倾向写的是"先 rquickjs，**若构建负担过重退 mlua**"。
**这条退路经实测不需要走**：rquickjs 在本机 221.9s 编过，且**不需要 libclang**
（`bindgen` 是可选特性，默认走预生成绑定）。原倾向里担心的"C 依赖编译"，
实测下来对三个候选**都成立**（wasmtime 也会经 `cc` 编译
`src/runtime/vm/helpers.c`），因此它**不构成区分度** —— 按原倾向的风险判断
去选型会得出错误结论。

**选 A 而非 B（mlua）的边界要说清楚**：两者在技术上都过验收、都能量产，
真正的差别是**脚本语言**（JS vs Lua）。选 A 的唯一决定性理由是上面第 3 条
（与前端语言统一、可生成类型声明）。如果将来发现用户更认 Lua，
B 在其余每一项上都不差，且在体积（0.52MB）与嵌入摩擦上更好。

**代价（必须记下来，不许淡化成"没有代价"）**

- workspace 的 `rust-version` 从 **1.85 抬到 1.87**（rquickjs 的 MSRV）。
  这是硬事实，不能靠继续声明 1.85 来掩盖。
- 引入第一个脚本引擎的 C 依赖：QuickJS 的 4 个 .c 文件经 `cc` 编译。
  冷构建 +221.9s，单文件可执行体积 +1.14MB。
- **隔离强度弱于 WASM，且不可用"沙箱"一词含糊过去。** 脚本在**进程内**
  执行，QuickJS 的缺陷会成为宿主进程的内存安全问题。因此 M7 **不得**把
  "安全执行不可信第三方脚本"作为能力承诺；能承诺的只是
  **"自己写的脚本不会因为死循环/异常而拖垮宿主"**（有超时与 `catch_unwind`）。
  这一条要同时写进 M7 文档与脚本控制台的 UI 提示，不能只写在 ADR 里。

**明确不做的事**：不做"脚本引擎抽象层"。与 ADR-0012 同一条推理 ——
现在只有一个引擎，抽象层是纯投机成本；等真要引入 WASM 时形态会清楚得多
（那时 JS 与 WASM 的宿主 API 差异是结构性的，不是一层 trait 能抹平的）。

**重新评估的触发条件**（任一满足即重开 D1）

1. 出现**真实的第三方二进制插件分发需求**（把插件交给自己不认识的人运行），
   而不是"自己的脚本库"；
2. 脚本 API 稳定到数月不再新增宿主函数，且宿主调用开销成为可测量的瓶颈；
3. rquickjs 停止维护，或 QuickJS 的 C 依赖在某目标平台编不过。

### ADR-0012 · D2 已决：主数据进 SQLite，派生物走独立文件

**状态**：已决（M4 前的阻塞决策门；完整分析见 [`docs/D2-STORAGE-ANALYSIS.md`](./D2-STORAGE-ANALYSIS.md)）

**决策**：工程库按**数据性质**分层，而不是按存储技术偏好二选一。

- **主数据**（用户的名字/注释/类型/书签/补丁/函数边界/代码数据标记）→ **SQLite**
  （`rusqlite`，`bundled` 静态链接），库文件即 `.bfp`。
- **派生物**（反汇编、函数、交叉引用、字符串表、CFG）→ **独立文件** `<target-hash>.bda`，
  自研紧凑格式，写临时文件 + **原子 rename** 发布。整体可删、可无条件重建。
- `bitflip-project` 的公开 API **不暴露 `rusqlite` 类型**：`bitflip-core` 是对外稳定契约，
  嵌入方不该被迫依赖 SQLite。

**理由（三条，按重要性排序）**

1. **两类数据的写入模式相反。** 主数据是"小而频繁的随机写"，派生物是"大而一次性的批量写"。
   任何单一方案都会在一边吃亏：纯 SQLite 让几十万条派生物走 INSERT（慢 + 库膨胀），
   纯自研日志让"按地址查注释"这类高频查询要自己维护二级索引。
2. **同库会把"可以失败"和"绝不能失败"绑在一根绳上。** 派生物写入是可以失败的
   （磁盘满、分析取消），用户注释绝不能失败。更重要的是，重新分析要"先删旧派生物再写新的"——
   同库的大事务一旦中断崩溃，用户会看到**半新半旧的分析结果，而它看起来和完整的没区别**。
   这正是 CLAUDE.md §7 明令禁止的"让界面看起来完整"。分开存则由 rename 的原子性天然保证
   派生物**要么全新、要么全旧**。
3. **`bitflip-project` 已把这条分界写成契约**（"主数据 vs 可再生派生物"），
   D2 只是在落实它，不是在推翻已有设计。

**明确否掉的原倾向**：D2 表格原倾向是"先用 SQLite 把功能做对，M6 后按基准决定是否引入自研日志层"。
**这个倾向在 M4 的语境下是错的** —— 它假设"以后换存储是局部的事"，但 M4 之后派生物的表结构
与读写路径会全面依赖 SQL，而用户已经建了工程库、存了注释。**迁移一个装着用户主数据的库，
比一开始就分开贵得多。** 现在分开的成本只是"两个文件、两个写入路径"，这是便宜的。

**明确不做的事**：不引入 ORM；不做"存储后端抽象层"。目前只有一个后端，
抽象层是纯粹投机成本；等真有第二个后端（如只读导出快照）再抽，那时形态会清楚得多。

**代价**

- 两套写入路径要各自维护与各自测试（但简化版的单一路径代价更大，见 §3.2）。
- `rusqlite` 的 `bundled` 特性要编 C，会拉长冷启动构建（本机 capstone vendored 编译已需 7m38s）。
- 派生物格式的版本演进要自己保证（用 `format_version` + 交叉校验 `target_sha256` 兜住）。

**重新评估的触发条件**（任一满足即重开 D2）

1. 基准显示注解落库 P95 **持续 > 50ms**（即 SQLite 确实撑不住）；
2. 派生物在 M5/M8 演化出**按范围频繁查询**的需求，而 mmap + 二分不够用；
3. 用户提出**多目标联合检索**（"在所有打开的工程里找这个字符串"）——
   那需要真正的数据库，而不是每目标一个文件。

### ADR-0011 · D3 已决：M2 只包 capstone 单后端，接口保持后端抽象

**状态**：已决（M2 末的决策门，依据 M2 的实际使用证据）

**决策**：M2 的 `Decoder` 只实现 capstone 一个后端。**不**在 M2 引入 iced-x86。
`Decoder` trait 保持后端无关（`decode_one` 返回结构化的 `DecodedInsn`，
不暴露任何 capstone 类型），因此将来加后端是纯增量工作。

**依据（M2 实测，不是预设）**

- capstone 的单后端已经覆盖了 M2 的全部需求：x86 / x86-64 / AArch64 / ARM /
  RISC-V / MIPS 的真实解码、`detail(true)` 下的读写寄存器集合与内存操作数、
  以及 CALL/JUMP/RET/INT/PRIVILEGE 的**语义分组**。流程判断走分组而不是
  匹配助记符字符串，这条在实现中被证明是可靠的。
- 引入 iced-x86 的收益（x86 文本格式更贴近微软习惯、单条指令属性更细）
  在当前阶段**还换不来代价**：它是第二个 vendored C 依赖之外的纯 Rust 依赖，
  但真正的问题是**双后端会让"指令长度"出现两个真相来源**。指令长度决定
  稀疏索引的键，两个后端在少数前缀组合上给出不同长度，会让索引出现
  不可复现的漂移 —— 这是本项目最不能接受的一类 bug（CLAUDE.md §7）。
- 分支目标语义已用测试固化：capstone 给的是**已解析的绝对目标地址**
  （`backend::relative_targets_are_resolved_to_absolute`）。将来换后端时，
  这条测试会立刻失败并提醒适配层做转换 —— 这正是"保持后端抽象"的具体价值。

**代价与触发条件**

- 代价：x86 的文本渲染目前用 capstone 的 Intel 语法，个别助记符的写法与
  MSVC 习惯略有差异（例如内存操作数里的 `+` 被省略成 `[rcx rdx]`）。
  这影响的是**可读性**，不影响结构化字段。
- 重新评估的触发条件（任一满足即重开 D3）：
  1. M6 的交叉引用阶段需要比 capstone 更细的 x86 语义（如显式标志位读写）；
  2. 用户反馈明确指出 x86 文本格式妨碍阅读；
  3. 遇到 capstone 无法正确解码、而 iced-x86 可以的真实样本。


### ADR-0018 · D5 拆细：只做反编译器的**有界子集**，不做控制流结构化

**状态**：已决（原定 M10 评审；因"还原为高级语言代码"被提前提出而提前决策）

**背景**：既有结论是"反编译器默认不做"。重新评估后发现，
**真正的理由不是工作量，而是价值冲突** —— 这一点改变了决策的形式。

Ghidra 官方文档说反编译器"以低阶语言为输入，**只能推断**"。
也就是说反编译器的核心输出按其定义就是**推断**，
而所有反编译器的默认行为（`var_1`、`a1`、`int64_t` 兜底）
恰恰是 `CLAUDE.md` §7 明令禁止的"用假名冒充识别结果"。
最危险的失败模式是**看起来合理的错误输出**，这不是靠更多工作量能解决的。

**决策**：把 D5 从"做/不做"的二元决策拆成四个**各自可停止**的子项：

| # | 子项 | 结论 |
| --- | --- | --- |
| 1 | 单基本块**表达式视图** | **做**（已实现，见 `docs/DECOMPILER-SCOPE.md`） |
| 2 | 有条件时的类型展示（**不推断**） | 做，下一轮 |
| 3 | 控制流结构化（if/while/for） | **不做**（见下） |
| 4 | 接入外部反编译器（`koute/ghidra-decompiler`） | 先花 1–2 周 spike 验证 |

**不做控制流结构化的三条理由**：

1. **理论上不可判定**。SAILR 论文原文：结构化选择"在最终意义上是不可判定的"。
   根源是源码→二进制是**多对一**映射，其逆不唯一 —— 不存在"正确"的结构，
   只有"更可能的"。输出 `while` 的反编译器在猜，这与 §7 直接冲突。
2. **"消除 goto"是错的**。SAILR 实测 7 355 个函数：DREAM 做到零 goto，
   但结构相似度从 22.5 恶化到 **45.99**（越差越高）。追求"看起来干净"
   会得到"事实上更错"的结果。
3. **有实证的静默失败**。Ghidra 因 3 MB 栈帧静默没定义栈变量，
   导致输出里**整条 `xor` 消失** —— 这正是 §7「不能悄悄少给数据」禁止的。
   对照组是 IDA 在 Positive SP Value 时**拒绝反编译**；本轮实现与之同向：
   翻不了就写注释并计数。

**已落地的诚实性约束**（都有测试锁住）：
每条语句带来源指令地址；`structured` 字段恒为 `false` 且必定产出 `FlatGoto` 说明；
没名字就输出入口地址（测试断言不含 `func_`）；间接跳转写明"目标未知"；
寄存器名必须来自 capstone 后端，**本模块不维护名字表**。

**关于寄存器名的实测教训**：本模块最初硬编码 `0 => rax, 1 => rcx, …`，
假定 `RegId` 是从 0 连续编号的序号。实际它是 capstone 的**原始编号**，
于是真实目标上 `RegId(44)`、`RegId(231)` 全判成未知，
绝大多数指令退化成"无法翻译"。改为**注入**名字解析器
（`CapstoneDecoder::register_name`），并留了回归测试
`namer_is_asked_with_raw_capstone_ids_not_a_compact_index`。

**重新评估的触发条件**：`koute/ghidra-decompiler` spike 成功
（Apache-2.0、零 FFI、纯 Rust、default features 与我们的架构几乎重合），
则决策从"写反编译器"变成"给反编译器输出套一层诚实性外壳"，量级完全不同。

**2026-10 更新：能力已验证，但诚实性验证**已做且结论是**不通过**。
本机实测编译并运行 2.1.0（见 `docs/research/dependency-probe-evidence.md`）：

- 能力是真的：`mov eax,1; add eax,2; ret` → `return 3;`，常量折叠正确。
- 但它输出 `func_0x00000000` 占位名（§7 第一条明文禁止），
  类型 `xunknown8` 也无法核对。
- **决定性的一条**：给它一段带分支的完整函数
  （`test edi,edi; je +5; mov eax,1; ret; xor eax,eax; ret`），
  输出是 `void func(void) { return; }` —— **整段逻辑消失，且没有任何提示**。
  输出看起来完全像一次成功。这正是 §7 所说的失败模式：
  不是说它算错了，而是**它不说自己没做出来**。
- 成本也量化了：rlib **212 MB**（capstone 是 8.2 MB，26 倍），首次编译约 8 分钟。

**所以触发条件收紧为**：只有当 spike 能证明它**不输出占位名**
且**能判断自己是否丢掉了代码**（覆盖不全时必须让我们知道），才重开本决策。
做不到的话，一个会说谎的分析结果比没有分析结果更糟，因为它会被用户相信。
选型全貌与替代方案见 `docs/DEPENDENCY-DECISIONS.md` §3。

**代价**：本子集能表达的东西有限 —— 单块内是确定的，块间关系只有 goto。
但这是当前唯一能同时满足"有用"与"说的是真的"的位置。
