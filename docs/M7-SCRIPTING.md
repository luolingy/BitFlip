# M7 脚本层：运行模型与脚本 API

> 状态：M7 进行中。本文既是使用手册，也是 PLAN §M7 验收标准 3
> （"脚本 API 有版本号与稳定保证"）的正式载体。
> 引擎选型与理由见 [`docs/D1-SCRIPT-ENGINE-ANALYSIS.md`](./D1-SCRIPT-ENGINE-ANALYSIS.md)，
> 决策记录见 [`docs/DECISIONS.md`](./DECISIONS.md) 的 ADR-0013。

## 1. 运行模型（请先读这一节）

### 1.1 脚本跑在**进程内**

脚本由嵌入的 QuickJS 引擎（`rquickjs`）在服务进程里直接执行，**不是**子进程、
不是 WASM 沙箱。这一点必须在任何介绍脚本能力的地方如实说明，因为用户会据此
决定"要不要把别人的脚本粘进来跑"。

### 1.2 能防什么，不能防什么

| 情形 | 行为 | 机制 |
|---|---|---|
| 死循环、长时间计算 | 被中断，主进程不受影响 | 墙钟超时 + QuickJS 中断回调（默认 5 秒） |
| 抛出异常 | 转成结构化错误回传，进程存活 | `catch_unwind` + `Error::Exception` 解析 |
| 宿主侧 panic | 转成错误回传，进程存活 | `catch_unwind` |
| 脚本申请超大内存 | **不防** | 未设置内存上限 |
| 恶意脚本读写宿主可访问的资源 | **不防** | 无系统调用白名单 |

**结论：脚本层不是安全边界。** M7 承诺的只有一件事 ——
"你自己写的脚本不会因为死循环或异常把宿主搞死"。
它可以让你放心地跑**自己的**脚本，不能让你放心地跑**别人的**。
当前 API 表面里也没有暴露文件、网络或进程能力，但那是"还没做"，
不是"做了防护"；请勿据此推论出安全性。

### 1.3 每次运行都是干净上下文

每次执行都会新建一个 JS 上下文，脚本之间不共享全局变量。同一宿主对象可以反复
执行脚本（控制台里连着跑几次），但每次运行开始时日志与暂存写入都会被清空 ——
否则上一次的日志会混进这一次的结果，上一次被丢弃的写入也会莫名其妙地跟着提交。

### 1.4 分析耗时不计入脚本超时

分析是惰性的：第一次读 `bitflip.functions` 才会构建分析结论。ntdll.dll 的全量
分析要 10.6 秒，而脚本默认上限是 5 秒 —— 如果让分析算在脚本头上，第一个读函数
列表的脚本会报"脚本执行超时"，而**那不是脚本的错**，用户会去改一段本来没问题的
代码。

所以调用方应当在执行脚本**之前**先预热（`Host::warmup()`），把分析结论与反汇编
提前算好，并在此期间显示"分析中"而不是"脚本超时"。预热失败不致命：读 API 会在
脚本真正用到那个能力时各自报出准确原因。

## 2. 版本号与稳定保证

```js
bitflip.apiVersion;   // 当前为 1
```

脚本可以据此判断自己能否在当前宿主上运行。

### 2.1 与 `bitflip-core` 的关系：镜像语义，不暴露类型

脚本看到的数据形状（`FunctionWire`、`XrefWire`、`InsnWire` …）与 HTTP
`/api/*` 返回的是**同一批结构**，也由同一份 Rust 定义序列化而来。这样做有两个
目的：

1. 验收标准 3 要求"与 `bitflip-core` 语义对齐，但不直接暴露内部类型"。脚本拿到
   的是**序列化后的 wire 形状**，不是 Rust 类型；内部结构重构不会自动变成脚本
   的破坏性变更。
2. 用户只需要理解一种数据形状。前端的 `web/src/api.ts` 类型定义同时就是脚本的
   参考手册，两边不会各自漂移。

### 2.2 演进规则

| 变更 | 版本动作 |
|---|---|
| 新增函数 / 新增字段 | 次版本号 +1，脚本无需改动 |
| 已有字段语义变化、删除函数、改参数含义 | 主版本号 +1，CHANGELOG 必须给迁移说明 |
| 仅内部实现变化 | 版本号不动 |

`bitflip.apiVersion`、`ANALYSIS_FORMAT_VERSION`、`DISASM_FORMAT_VERSION`
三者**独立演进**：它们描述的是不同层面的契约（脚本 API / 分析结论形状 / 反汇编
分页形状），把版本号捆在一起只会让某一层的无关改动触发另一层的升级声明。

## 3. API 表面

全局对象 `bitflip`。地址参数接受三种写法，都指向同一个位置：

```js
bitflip.functions.at('0000000140009218');   // 定长小写十六进制（推荐）
bitflip.functions.at('0x140009218');        // 带前缀
bitflip.functions.at(0x140009218);          // 数字
```

数字写法仅在该地址 **≤ 2^53** 时可靠，见 §7.1。

### 3.1 日志

```js
bitflip.log(value);    // 信息
bitflip.warn(value);   // 警告
bitflip.error(value);  // 错误
```

参数按 JS 的 `String()` 语义强制转换，所以 `bitflip.log(count)`、`bitflip.log(a, b)`
这些写法都按控制台的直觉工作。日志随运行结果一起回传到 UI，并带上级别。

### 3.2 目标与分析汇总

| 调用 | 返回 |
|---|---|
| `bitflip.target` | 目标识别结论对象；**没有打开目标时为 `null`** |
| `bitflip.notes()` | 分析过程的降级说明（字符串数组） |
| `bitflip.counts()` | `{ functions, blocks, xrefs, strings, cfgs }` |

`notes()` 不是装饰。分析器拿不到某些信息时会写一条降级说明（例如"ELF 无
`.eh_frame`，函数边界靠线性扫描"）。脚本读不到这些，就会把一份降级结果当成
完整事实导出成清单 —— 这正是 `CLAUDE.md` §7 禁止的。**导出清单的脚本应当把
`notes()` 一并带上。**

### 3.3 函数

| 调用 | 返回 |
|---|---|
| `bitflip.functions.count()` | 函数总数 |
| `bitflip.functions.page(offset = 0, count = 512)` | 页对象（见 §4） |
| `bitflip.functions.at(addr)` | 起始地址**正好**等于 `addr` 的函数，否则 `null` |
| `bitflip.functions.containing(addr)` | 包含该地址的函数，否则 `null` |

`at` 与 `containing` 的区别是刻意的：`at` 回答"这里是不是一个函数的开头"，
`containing` 回答"这个地址属于哪个函数"。

### 3.4 交叉引用

| 调用 | 返回 |
|---|---|
| `bitflip.xrefs.count()` | 引用总数 |
| `bitflip.xrefs.page(offset = 0, count = 512)` | 页对象 |
| `bitflip.xrefs.at(index)` | 第 `index` 条（下标从 0 起），越界为 `null` |
| `bitflip.xrefs.from(addr)` | 从 `addr` 出发的全部引用（数组） |
| `bitflip.xrefs.to(addr)` | 指向 `addr` 的全部引用（数组） |
| `bitflip.xrefs.search(filter)` | 页对象 |

顺序是确定的（发起地址升序，同址内按类型），所以 `at(index)` 在同一个目标上是
稳定可复现的。

`search` 的过滤条件：

```js
bitflip.xrefs.search({
  kinds:     ['call'],                        // 类型白名单
  sources:   ['disasm'],                      // 来源白名单
  fromRange: ['0000000140001000', '0000000140002000'],  // 左闭右开
  toRange:   ['0000000140009000', '000000014000a000'],
  offset:    0,
  count:     512,
});
```

`kinds: []`（**空数组**）与不传 `kinds` 是两件事：前者是"一个类型都不要"
（匹配 0 条），后者是"不按类型过滤"。界面上一旦出现"全部取消勾选反而显示全部"，
用户就再也不信任过滤器了。

### 3.5 字符串

| 调用 | 返回 |
|---|---|
| `bitflip.strings.count()` | 字符串总数 |
| `bitflip.strings.page(offset = 0, count = 512)` | 页对象 |
| `bitflip.strings.at(addr)` | 该地址上的字符串，否则 `null` |

### 3.6 指令

需要宿主注入反汇编结果，否则调用会明确报错（而不是返回空数组）。

| 调用 | 返回 |
|---|---|
| `bitflip.insns.page(from, count = 512)` | 指令页对象（游标语义：从 `from` 起的第一条开始） |
| `bitflip.insns.at(addr)` | 起始地址**正好**等于 `addr` 的指令，否则 `null` |

`at` 是精确查找，不是游标。这一条很重要：线性扫描会把未对齐的字节也解出指令，
所以"某条指令 + 1"上**有可能**真的存在一条指令起点；而游标语义会让
`insns.at(addr)` 在 `addr` 不是起点时返回**下一条**指令，于是
"这个地址有指令吗"这类判断会静默算错。

### 3.7 读取字节

```js
bitflip.readBytes('0000000140009218', 16);   // → 小写十六进制字符串
```

单次上限 1 MiB。超限**报错**而不是静默截断：返回一个被截短的数组会让脚本以为
"那段内存就这么多"。读不到时抛异常并说明地址与原因。

### 3.8 写入：注释与名字

```js
bitflip.setComment(addr, 'memcpy(dst, src, n)');
bitflip.setName(addr, 'my_function');
bitflip.get(addr, 'comment');   // → 字符串，或 null
bitflip.stagedCount();          // → 本次运行已暂存的写入条数
```

`get` 的 `kind` 取值与工程库一致：`name` / `comment` / `type` / `bookmark` /
`patch` / `function-boundary` / `code-data`。取值非法时会抛异常并列出合法值。

写入语义见 §5。

### 3.9 进度上报

```js
bitflip.progress(done);                    // 总数未知
bitflip.progress(done, total);             // 有确定总数
bitflip.progress(done, total, '正在处理 x.dll');
```

批处理进度必须由**脚本主动上报**：只有脚本知道总共要做多少件事。宿主不会替你
估算 —— 按"已暂存条数"之类的信号猜，会在"这一轮不写任何东西"的阶段停住不动，
看起来跟卡死一模一样。

`total` 省略时界面显示"进行中"而不是 `0%`。**不要报一个假的 0**：进度条停在
0% 与"正在进行但总量未知"是两种完全不同的状态。

进度在每次运行开始时清空。上一次的 90% 不会留在这一次的界面上。

## 4. 分页与遍历

### 4.1 页对象的字段

```js
{
  total:     12105,   // 过滤后的总条数
  requested: 512,     // 你这次要多少
  skipped:   0,       // 实际跳过了多少（越界的 offset 会收敛到 total）
  returned:  512,     // 本页实际给了多少
  truncated: 11593,   // 后面还剩多少没给
  items:      [ ... ]
}
```

`requested` 与 `truncated` 都必须有：只看 `returned` 会分不清"数据就到这儿了"
还是"我自己要少了"；只给总条数则会让人以为一次能全拿走。

单页上限 4096 条（`MAX_PAGE_SIZE`）。请求超过上限会被收敛到 4096，但
`requested` 仍然如实回报你原本要的数量。

### 4.2 为什么不提供 `all()`

ntdll.dll 一个目标就有 66778 条交叉引用。`xrefs.all()` 等于给脚本递上一颗定时
炸弹：一次调用物化 6 万多个 JS 对象，超时上限一到就白跑，而且失败信息
（"脚本超时"）完全指不出真正的原因。

**所以遍历必须分页，或者按下标。** 两种正确写法：

```js
// 写法一：按下标（每轮只物化一条，最适合"逐条判断"）
const n = bitflip.xrefs.count();
for (let i = 0; i < n; i++) {
  const x = bitflip.xrefs.at(i);
  if (x.kind === 'call') { /* ... */ }
}

// 写法二：分页（每轮物化一页，最适合"批量处理"）
const total = bitflip.functions.count();
for (let off = 0; off < total; off += 512) {
  for (const f of bitflip.functions.page(off, 512).items) {
    /* ... */
  }
}
```

如果确实需要一整份快照（例如生成导出文件），也要自己按页拼接，并在这个过程中
保持可中断 —— 这样被中断时用户能知道进行到哪儿了。

### 4.3 越界的 `offset` 不报错

`page(offset)` 的 `offset` 超过总数时返回空页，`skipped` 收敛到 `total`。
这是分页的正常边界情形（循环多跑一轮不该炸），不是错误。

## 5. 写入与回滚

### 5.1 先暂存，正常结束才提交

写入先进入暂存区，脚本**正常执行完毕**时才一次性提交到工程库。以下情形全部丢弃：

- 超时被中断；
- **被用户主动取消**（见 §5.4）；
- 抛出异常 / 语法错误；
- 宿主侧 panic。

这样"跑到一半被打断"不会留下一份半成品结果。同一个 `(地址, 类型)` 反复写入时
**后写覆盖先写**，`stagedCount()` 统计的是去重后的条数。

### 5.2 脚本能读到自己刚写的东西

`bitflip.get` 先查暂存、再查工程库。否则"没有名字才命名"这类脚本会在同一次运行里
重复劳动。

### 5.3 提交可能部分成功 —— 这是唯一含糊不得的结局

提交是逐条写入的。如果中途失败，返回的错误会**同时给出已写入条数与总条数**，
界面必须把这两个数如实显示出来。含糊其辞会让用户以为要么全成要么全不成。

没有打开工程库时提交会失败并说明原因；脚本本身仍然可以正常跑完（例如只做分析
和日志的脚本）。这种情况下结果里会带"尝试写入的条数"，界面应当显示
"脚本写了 N 条，但没有工程库可存"，而不是一个干巴巴的 0。

### 5.4 外部取消

控制台（以及任何长时间运行的批处理入口）提供"停止"。取消请求送到脚本引擎后，
解释器会在下一次中断检查时停下，行为与超时一致：**暂存写入全部丢弃**。

取消与超时在报错上**分开**：

| 结局 | 含义 | 用户该做什么 |
|---|---|---|
| 已取消 | 是你自己按的 | 什么都不用改 |
| 超时 | 脚本太慢 | 优化脚本或提高上限 |

把两者合并成一条"超时"提示，会让用户去改一段本来没问题的代码。

取消请求只在**当前这一次运行**内有效。没有脚本在跑时发出的取消会被忽略并返回
"没有可取消的运行"，而不是留给下一次运行 —— 否则用户手快按一下，下一个脚本
刚启动就被掐掉，而现象是"莫名其妙地立刻失败"。

## 6. 错误与日志

脚本异常会转成结构化错误回传到 UI，包含消息、**行号**与调用栈。行号来自
QuickJS 的栈信息（引擎本身不在错误对象上设 `lineNumber`），所以脚本文本的
行号是可信的。

日志按级别（`info` / `warn` / `error`）与脚本自己的异常分开呈现：日志是脚本
主动说的话，异常是脚本没跑下去的原因，两者不该混在一个列表里。

## 7. 已知陷阱

### 7.1 地址是**字符串**，而且不要用位运算

wire 上地址统一是定长小写 16 位十六进制字符串（`0000000140009218`）。
需要参与计算时用 `parseInt(x, 16)`。

两个坑：

- **不要用位运算**。JS 的 `&` `|` `<<` 会把操作数截成 **32 位**，而 PE 的地址
  常在 `0x140000000` 以上。`base & ~0xFFF` 会算出负数再变成乱的十六进制串。
  要对齐请用算术：

  ```js
  const lo = Math.floor(base / 4096) * 4096;   // 对
  const lo = base & ~0xFFF;                    // 错：> 2^32 时截断
  ```

- **数字写法有精度边界**。超过 2^53 的数字在 JS 里已不可精确表示，所以
  `bitflip.*` 的数字参数会被拒绝而不是悄悄取一个近似的值。大地址请用字符串。

### 7.2 "没有能力"与"没有数据"必须区分

- 没有打开目标时调读 API：**抛异常**，不是返回 0。
  返回 0 会让脚本写出"这个目标没有函数"的结论，而真相是"没打开目标"。
- `bitflip.target` 在无目标时是 `null`，不是空对象 —— 空对象会被
  `Object.keys(t).length === 0` 之类当成"有目标但字段缺失"。
- 没有注入反汇编结果时 `bitflip.insns.*` 抛异常，不是返回空数组。
- 按地址查不到东西时返回 `null`，不是 `undefined`。"这个地址还没有注释"是
  合法的预期结果，不该与"你取错了键"长得一样。

### 7.3 地址基址

PE 映像的地址是**虚拟地址**（含映像基址）。历史上曾有一处缺陷让符号表来的函数
落在节内偏移上（`0x8218`），而分析发现的函数落在虚拟地址上（`0x140009218`），
同一个映像里出现两套地址。该缺陷已修复（见 CHANGELOG），但如果你在别处看到
可疑的低地址，先怀疑基址而不是数据。

## 8. 尚未提供

以下能力 PLAN §M7 列在脚本 API 交付物里，但**当前版本没有**。调用不存在的成员
会得到 JS 的 `TypeError`；本文不把它们写成"可用"，以免脚本作者照着一份不存在的
API 写代码。

- `bitflip.symbols.*`（符号来源与候选查询）
- 注册自定义分析 pass
- 生成补丁（`patch` 类型目前只能通过 `get`/暂存写入机制间接使用，没有专门的生成接口）
- 自定义视图数据源

## 9. 示例脚本

内置示例脚本集（PLAN §M7 交付物之一：批量重命名、导出函数清单、识别常见库调用
模式）由 `bitflip-script` 以源码内嵌的方式随二进制发布，通过脚本库界面读取，
不经文件系统 —— 这样脚本与它面向的 API 版本始终一致，也不会因为运行目录不同而
消失。每个示例都带注释说明它用到哪些 API、以及在什么情况下会如实报错而不是给出
空结果。

其中"识别并注释全部 `memcpy` 调用"这一份同时是 PLAN §M7 验收标准 1 的载体，
其端到端行为由 `crates/bitflip-script/tests/read_api.rs` 里的
`acceptance_1_identifies_memcpy_calls_and_annotates_them_end_to_end` 守着。
